# Web 交互动效基础规范

版本：1.0 · 资料核对日期：2026-10-15 · 适用范围：跨项目、跨框架的 Web 交互设计与质量评价。

本规范回答四个问题：为什么动、怎样选择、不同交互怎样保持一致、如何证明它有帮助。Transitions.dev 是主要设计参考，不是本规范的发布者或认证方。

## 1. 阅读约定与参考边界

全文采用以下来源标记；标记作用于所在段落或明确标注的表格：

- **【官方】**：在固定版本的 Transitions.dev 资料中可以直接核对的描述、参数或方法。
- **【归纳】**：从参考效果中提炼的通用设计原则，不代表官方原文。
- **【建议】**：本规范为完整性、可用性或验证而补充的建议，可依据实际约束调整。
- **【外部标准】**：来自 W3C 等资料的要求或指导，保留其适用条件和等级。APG 模式指导与浏览器性能建议不等同于 WCAG 成功准则。

“应”表示本规范推荐的基线；例外需要能解释用户收益和验证结果。“可以”表示可选手段。官方参数只是参考起点，不能仅凭数值一致就认定设计正确，也不能据本规范宣称整体符合 WCAG。

### 1.1 Transitions 是什么

【官方】Transitions.dev 提供交互动效展示、可复用的 CSS recipes、可调变量与面向编码 Agent 的使用指南。官方仓库还包含辅助工具；本规范仅研究交互设计依据，不要求采用这些工具。[官方 README][readme]

| 资料 | 解决的问题 | 可提炼的通用内容 | 不直接升级为通用规范的内容 |
|---|---|---|---|
| 动效示例 | 看清变化的节奏、方向和视觉关系 | 状态连续性、层级、强调程度 | 展示页布局、配色、品牌风格与演示数据 |
| CSS recipes | 查看一个具体效果如何表达 | 进入/退出关系、动作范围、减少动态处理 | 选择器、DOM 结构、测量方式、具体曲线与数值 |
| Motion tokens | 用有限词汇描述与调整动效 | 按用途选参数、一致性和可解释的例外 | 全量变量集合及其默认值 |
| Agent 指南 | 帮助 Agent 将需求匹配到 recipe | 先识别交互用途，再选效果；合适时选择较低开销方案 | 安装、复制代码及工具执行步骤 |

【归纳】四者可理解为：示例帮助观察，recipe 提供具体表达，tokens 提供可调语言，指南帮助选择。适合参考的问题包括突兀的状态切换、难以理解的出现位置、缺少操作反馈、过多互不一致的节奏。动效不能弥补不清楚的文案、错误的状态、不合理的信息结构或无法操作的控件。

### 1.2 资料中的差异如何处理

【官方】本次固定版本的指南仍有“32 个”的描述，但索引列到了 35；README 的部分数量更旧。数量不是本规范的能力或质量依据，以实际读到的条目为准。[指南][guide]

【官方】`_root.css` 同时包含共享尺度和单个效果的调节变量，并非每个效果变量都引用共享 token。例如共享时长表把 toast close 对应到 350ms，而具体 toast 默认关闭时长为 250ms。不能假定复制共享 token 就能统一所有效果，也不能按“数字接近”机械替换。[tokens][tokens]

【建议】遇到类似差异，先确定所需交互语义，再比较具体 recipe 与参数；保留有理由的差异。指南中的复制要求属于其使用方式，不成为跨项目设计约束。

## 2. 原则：动效应该帮助用户理解什么

以下为【归纳】，验证要求为【建议】。

| 目的 | 选择依据 | 保持静态更合适的情况 | 可观察的验证 |
|---|---|---|---|
| 状态变化 | 变化不容易被察觉，且旧状态与新状态存在关联 | 高频更新造成持续闪动，或变化本来已经清楚 | 用户能指出现在的状态，不需要等动画结束 |
| 空间关系 | 需要说明来源、去向、展开范围或层级 | 两个对象没有空间关系，移动反而暗示错误联系 | 方向与触发位置、阅读方向和实际层级相符 |
| 操作反馈 | 用户需要知道输入已被接收、正在处理或已完成 | 静态文字、按下态或选中态已足够 | 反馈及时，过程状态和真实结果没有混淆 |
| 注意力层级 | 新信息确实需要被注意 | 内容与当前操作无关，重复提醒打断阅读 | 重要变化可见，次要变化不会争夺注意力 |

【建议】先用一句话描述“用户需要理解什么”，再选择效果。无法说明收益时，优先使用静态变化。对偶发、重要变化可以适度强调；对高频操作要降低运动幅度和重复成本。品牌表达可以是附加收益，但不能牺牲可操作性或信息完整性。

## 3. 选择依据：建立动效设计语言

### 3.1 各维度怎样选

下表为【归纳／建议】，不是官方数值标准。

| 维度 | 作用 | 选择依据与边界 |
|---|---|---|
| 时长 | 决定变化可被追踪的时间 | 高频、局部反馈宜短；复杂关系可留更多观察时间。持续更久不代表更自然，短到难以察觉也可能失去目的 |
| 缓动 | 描述速度如何变化 | 减速有助于落定；连续往复需要衔接；匀速适合表达持续过程。弹性只在额外强调有价值时使用，避免暗示状态反复 |
| 延迟 | 区分意图或组织顺序 | 悬停提示可用短延迟避免误触发；直接操作应先反馈。延迟不能变成等待装饰效果的门槛 |
| 位移 | 表达来源、方向和关联 | 用足以看清关系的距离；大面积、长距离移动成本更高。不要让无关对象沿相同路径制造假关联 |
| 缩放 | 表达层级、出现和轻度强调 | 保持内容可读、位置可追踪；少量缩放通常比强烈弹跳更克制。大区域缩放会放大视觉运动 |
| 透明度 | 表达显隐、旧新内容交接 | 适合关系简单的变化；避免两段文字同时可读造成重影。透明不等于不可聚焦或对辅助技术隐藏 |
| 模糊 | 弱化过渡中的细节 | 可选装饰；会降低瞬时可读性并增加渲染成本。文字密集、低性能或减少动态场景优先省略 |
| 错峰 | 让一组变化体现顺序 | 仅在顺序有意义时使用；总等待随数量增长，不能让末尾内容长期不可用 |

【建议】同时考虑“多久开始反馈”和“多久结束视觉变化”。用户可以立即得到已接收反馈，视觉过渡稍后完成。顺序播放的总时间包含各段时长、间隔及错峰；并行播放不能简单相加。不要只检查某一个 duration。

### 3.2 如何使用语义化 motion tokens

【官方】指南强调按**用途**匹配 token，而不是按原有数字找最近值。[指南的 Motion tokens 与 refine 说明][guide]

【建议】语义化意味着能回答“这个值负责什么”：例如“轻反馈”“表面进入”“表面退出”“强调反馈”。这些是本规范的说明性词汇，不是要求新增的变量名。先识别已有语义，同类用途保持一致；只有确实不同的交互需要，才保留独立参数。

下面仅摘取少量官方参考，完整定义见 [固定版本 tokens][tokens]：

| 官方 token | 该版本参考值 | 官方所举用途 | 使用时需要判断 |
|---|---|---|---|
| `--duration-quick` | 150ms | 弹层关闭、文字替换等 | 是否足以理解变化，是否存在额外串行等待 |
| `--duration-fast` | 250ms | 弹层打开、选中指示器移动等 | 频率、范围和内容可用时间 |
| `--duration-stagger` | 40ms | 相邻项目的错峰间隔 | 总数量造成的累计延迟 |
| `--ease-smooth-out` | `cubic-bezier(0.22, 1, 0.36, 1)` | 表面显隐与位置变化等 | 是否符合动作的起止关系 |
| `--distance-micro` | 4px | 文字替换 | 内容是否仍能轻松阅读 |
| `--scale-large` | 0.96 | modal 显隐 | 名称描述其体系内的缩放幅度，不能解释为通用尺寸 |

【建议】完整的动效约定至少表达：触发条件、变化目的、运动属性、节奏、结束状态、中断策略、减少动态方案。只有一张毫秒表，不能构成设计语言。

简短示例：选择变化立即成立；指示器从当前位置移动至新位置；快速改选时转向最新目标；减少动态时直接落位。这里的核心是选择连续性，并不依赖固定时长。

## 4. 通用模式：从用户需要理解的变化出发

本节每项“官方参考”描述来源能力；“选择、误用、验证”为【归纳／建议】。

### 4.1 出现与消失

- **用户需要理解**：什么出现了，它与当前内容是什么关系，关闭后回到哪里。
- **动效如何帮助**：淡入淡出表达显隐，轻缩放表达浮于原内容之上的表面；运动方向应符合真实关系。
- **官方参考**：[Modal open / close][modal] 展示中心缩放的进入与退出；该版本参考打开 250ms、关闭 150ms。
- **适用条件**：表面的出现需要建立层级。仅提示小范围状态变化时，静态提示或淡变可能足够，不必引入更重的表面。
- **不适用与误用**：把所有内容都做成弹出；用相同长时长处理每次关闭；透明退出后仍拦截操作；为了演完动画延迟焦点处理。
- **验证**：进入、退出、退出中重新打开都能到达正确状态；焦点留在可理解的位置；关闭后不会留下不可见的交互区域。

### 4.2 展开与收起

- **用户需要理解**：哪些内容属于这个标题，收起隐藏了哪一部分。
- **动效如何帮助**：让内容区域的变化和展开标记保持对应，减少突然挤动造成的迷失。
- **官方参考**：[Accordion expand][accordion] 通过区域高度变化与箭头翻转表达展开状态；具体 grid 技巧属于实现细节。
- **适用条件**：局部内容与触发器有明确归属，尺寸变化可以被稳定呈现。
- **不适用与误用**：长内容展开产生大面积运动；为控制动画而裁掉内容；视觉收起后隐藏控件仍能获得焦点；箭头与真实状态不一致。
- **验证**：短长内容、内容动态变化、快速反向操作均能正确落定。若正在隐藏的内容含焦点，焦点去向应有明确安排。区域重排过大时采用静态展开或更轻的提示。

### 4.3 切换与替换

- **用户需要理解**：哪项被选中，什么内容被替换，是否仍在同一个上下文。
- **动效如何帮助**：移动选中指示器表达连续选择；轻量交接表达旧内容变成新内容。
- **官方参考**：[Tabs sliding][tabs-recipe] 展示选中指示器移动；[Text states swap][text-swap] 展示文字退出后新文字进入。前者首屏定位与尺寸调整不播放切换动画。
- **适用条件**：互斥选项有明确位置关系，或同一位置的状态发生可理解的变化。
- **不适用与误用**：让指示器移动代替选中语义；文字不断翻动难以阅读；排队播放已经过期的选择；让键盘必须等动画结束。
- **验证**：快速连续选择后显示最新有效状态；焦点、选中态、内容一致；初次显示没有从错误位置滑入。高频数据更新可以直接替换，保留稳定标签帮助比较。

### 4.4 加载与完成

- **用户需要理解**：内容尚未准备好，系统仍有响应，何时可以使用结果。
- **动效如何帮助**：适当占位维持空间预期，轻微活动表达处理中，结果出现后结束活动。
- **官方参考**：[Skeleton loader and reveal][skeleton] 展示占位与内容的交接；其实际揭示函数与演示重放计时是分开的。
- **适用条件**：等待具有可感知长度，且能够合理预估内容结构。未知结构可以用简洁的状态提示。
- **不适用与误用**：为了播放完整循环而延迟已就绪内容；用演示计时代表真实完成；错误发生后仍无限加载；未知进度伪装成准确百分比。
- **验证**：即时完成、长等待、失败、取消均有清楚状态；内容就绪即可使用；关闭动态后仍能知道正在处理；占位不会制造严重布局跳变。

### 4.5 成功与错误反馈

- **用户需要理解**：操作是否完成，或哪里需要修正。
- **动效如何帮助**：有限强调吸引注意，随后保留清楚、可读的结果。
- **官方参考**：[Success check][success] 展示完成标记；[Error state shake][error] 展示抖动、错误样式和提示，并包含自动恢复的示例。
- **适用条件**：重要但不频繁的结果需要确认，或用户可能忽略局部错误。抖动和庆祝都是可选手段。
- **不适用与误用**：每次成功都强烈庆祝；连续输入不断抖动；仅靠颜色或运动表达错误；机械沿用错误提示的自动消失计时。
- **验证**：结果与真实状态一致；错误未解决时，修正所需信息仍然可获得；减少动态时仍有文字或语义明确的标记。短暂提示只有在不承担唯一必要信息时才适合自行消失。

### 4.6 悬停、聚焦和选中

- **用户需要理解**：哪些对象可操作、当前焦点在哪里、哪些状态已被选定。
- **动效如何帮助**：轻量反馈确认当前目标，选中后的稳定外观表达持久状态。
- **官方参考**：[Tooltip open/close][tooltip] 展示悬停或聚焦提示及短延迟；[Toggle][toggle] 展示开关位置变化；选中位置关系可参考 [Tabs sliding][tabs-recipe]。
- **适用条件**：提示提供补充说明，状态变化有清楚语义。可选的鼠标装饰不必在键盘下逐帧复刻，但信息和操作能力应等价。
- **不适用与误用**：把必要信息只放在 hover；把聚焦当作已选中；焦点提示必须等淡入；指针快速经过仍弹出迟到提示；开关弹跳造成状态反复的错觉。
- **验证**：键盘可用、焦点立即可见、触屏不依赖悬停；取消悬停或转移焦点后不会出现过期提示。适用的额外提示满足可关闭、可悬停、持续显示要求，见第 6 节。

## 5. 连续性与可中断性

【归纳】连续性不是要求所有动画都完整播放，而是让用户理解当前状态如何变成下一状态。进入与退出应共享对象身份和合理路径，但不要求完全镜像或相同时长。

【建议】按以下情境判断，而不是默认禁用操作等待动画结束：

| 情境 | 推荐行为 | 需要避免 |
|---|---|---|
| 进入中关闭、退出中打开 | 从当前可见状态继续或反向；静态落位也是可接受退化 | 先跳回起点再重播、已关闭的表面突然复现 |
| 同一动作反复触发 | 需要再次确认时给轻反馈；同一目标不必重复完整动画 | 重复输入造成队列越积越长 |
| 快速切换 | 对表达当前状态的动效，以最新有效目标为准 | 旧计时或旧完成通知覆盖新状态 |
| 连续事件有独立意义 | 保留事件信息，可合并视觉呈现 | 为追求“最新”丢掉必须保留的信息 |
| 用户取消 | 表达实际取消结果或待确认状态，停止无意义运动 | 只停止动画却继续显示错误的过程状态 |
| 改变尺寸或内容 | 重新保持目标位置与可读性，必要时直接落位 | 把初始化和重排误演成一次用户操作 |
| 减少动态或关闭动画 | 直接形成正确终态，保留反馈与操作能力 | 依赖必然发生的动画结束事件才能解锁界面 |

【建议】最低检查序列：打开→立刻关闭→重新打开；连续切换多个目标；处理中取消；内容或尺寸在过渡中改变；动画进行中启用减少动态偏好。每种情况都检查视觉、语义、焦点和可操作性，而不只看最终截图。

## 6. 无障碍与性能边界

### 6.1 减少动态不是隐藏信息

【官方】所读取 recipes 提供 `prefers-reduced-motion` 处理，并要求保留。[指南][guide]

【建议】减少非必要位移、缩放、弹跳、模糊和循环活动，可直接切到终态，或在适合时采用更轻的透明度变化。减少动态不是把所有状态提示删掉。不能只检查媒体查询存在：还要实际启用偏好，确认等待逻辑、最终可见性、错误提示和焦点仍正确。

【外部标准】WCAG 2.2 的 [2.3.3 Animation from Interactions（AAA）][wcag-motion] 要求交互触发的运动动画可被禁用，除非对功能或信息表达必不可少。它不是所有 AA 检查中的同一条强制要求。本规范仍建议将减少动态作为基本体验设计的一部分；必要运动需具体说明为何不可替代。

### 6.2 键盘、焦点和状态语义

【外部标准】键盘操作、合理焦点顺序与可见焦点分别参见 WCAG [2.1.1][wcag-keyboard]、[2.4.3][wcag-order]、[2.4.7][wcag-focus]；状态消息参见 [4.1.3][wcag-status]。视觉动画不能代替这些能力。

【建议】焦点不跟随装饰性物体移动，不留在已经隐藏或移除的内容中。选中、展开、错误和处理状态应具有可感知且可由辅助技术识别的表达；不需要为每一帧运动发出播报。

【外部标准／建议】Tabs 的方向键、进入方式和自动／手动激活应参考 [WAI-ARIA APG Tabs][apg-tabs]，具体选择取决于内容能否及时显示。官方动效 recipe 的点击示例不等于完整 Tabs 行为。无有效选中项时仍应为可用选项保留合理键盘入口；禁用项的焦点策略按控件语义明确，不由滑动效果决定。

【外部标准】对于 hover/focus 触发的额外内容，WCAG [1.4.13（AA）][wcag-hover] 在适用条件下要求可关闭、可悬停且持续显示，并规定了例外。不能因为官方提示动画离开触发器就消失，直接认定整套提示行为符合该要求。

### 6.3 闪烁、循环与阅读干扰

【外部标准】WCAG [2.3.1（A）][wcag-flash] 对每秒闪烁次数及一般／红色闪光阈值有明确要求；不是仅凭动画时长或肉眼“温和”判断。存在高对比快速闪烁时，应按阈值评价。

【外部标准】[2.2.2（A）][wcag-pause] 对自动开始、超过五秒、与其他内容并行呈现的移动／闪烁／滚动信息，通常要求暂停、停止或隐藏机制，必要活动有例外；自动更新信息另有控制要求，不套用五秒门槛。

【建议】没有触及上述条件，也不意味着持续装饰值得保留。长时间阅读区域优先安静；对处理指示可用静态文字补足，避免为了“还活着”不断占用注意力。

### 6.4 渲染成本与收益

【外部指导】浏览器性能指南建议尽量使用 transform 和 opacity，检查布局、绘制与合成成本，并谨慎使用 `will-change`。[web.dev 性能指南][performance]

【建议】这些是优先选择，不是无条件禁令：展开区域可能确实需要改变布局；transform 也不能保证任何场景都流畅。模糊、大面积透明叠加、多个并发动画或大量独立图层可能产生显著成本。是否保留，要依据实际面积、内容数量、设备能力与测量结果。

【建议】不要因 recipe 出现 `will-change` 就将其升级为全局默认。关注长期图层和内存成本；先减少无必要属性、缩小运动范围或简化效果，再判断是否需要额外优化。仅在常用设备上看起来顺滑，不足以证明低性能设备可用。

## 7. 验证方式：怎样评价一个动效

### 7.1 六个判断维度

以下为【建议】。每项应有观察结果，不能仅给“流畅、自然”的评价。

| 维度 | 要回答的问题 | 合适的证据 |
|---|---|---|
| 明确目的 | 它帮助用户理解哪种变化？ | 一句目的说明；与静态方案的对照 |
| 理解变化 | 来源、目标、选中和结果是否清楚？ | 观察操作后的解释与误判，而非只问好不好看 |
| 及时且一致 | 是否及时响应，同类变化是否可预期？ | 实际反馈延迟、完整序列与快速操作观察 |
| 阅读和操作 | 是否妨碍阅读、点击、键盘或焦点？ | 长内容、连续操作、键盘和辅助技术验证 |
| 信息完整 | 减少或关闭动态后是否仍能完成同一操作？ | 静态／减少动态模式下的状态与结果检查 |
| 收益与成本 | 视觉收益是否值得渲染和注意力成本？ | 有／无该效果的性能对照与用户表现 |

### 7.2 四类验证各自证明什么

| 类别 | 可以证明什么 | 不能单独证明什么 |
|---|---|---|
| 设计评审 | 意图、方向、层级、节奏和一致性是否合理 | 真实可操作性、运行性能、用户收益 |
| 功能验证 | 状态、键盘、焦点、中断、减少动态是否按预期工作 | 大规模用户理解度或所有设备性能 |
| 性能测量 | 指定设备、浏览器和负载下的帧时间、掉帧、长任务、布局／绘制与资源成本 | 用户是否理解或喜欢该效果 |
| 真实用户研究 | 特定人群与任务中的理解、完成效率、错误、干扰与不适 | 未覆盖人群的结论或无条件因果关系 |

【建议】性能记录注明设备、浏览器、内容规模和并发情境；不把固定帧率口号当作全场景验收线。用户研究区分偏好和实际表现，样本与场景不足时说明局限；没有研究时不宣称“已经提升效率”。

### 7.3 最小评价记录

【建议】每个有实际用途的动效，只需能简要回答：

1. 用户要理解什么，静态方案是否已经足够？
2. 为什么选择这个模式、范围和节奏？
3. 进入、退出、重复、中断与取消分别怎样结束？
4. 减少动态、键盘和辅助技术下信息是否完整？
5. 做过哪些设计观察、功能检查和性能测量？哪些仍未验证？
6. 若保留例外，它带来的收益是什么，有什么证据？

这是一套评价问题，不要求每个轻微反馈都开展完整研究。覆盖范围随交互频率、运动面积、复杂度和用户风险增加。
